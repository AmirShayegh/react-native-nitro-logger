## Executive summary

The fix pass was the right response to the last review. All 17 prior findings were genuinely addressed — several better than asked: the purge fix uncovered and closed two adjacent races nobody had reported, the CI fix corrected the root cause (`$TURBO_ROOT$` resolution) rather than the noticed glob, and the eslint fix landed the recommended exhaustiveness test rather than two spot patches. ### Highlights per cluster

**#1 Purge (closed).** `FileDestination.purge()` now guards `disposed` *before* touching the sink (`src/destinations/FileDestination.ts:265-274`), so even a third-party sink answering `durable:true` can't become the destination's answer. Both native adapters gained `mayHaveArtifacts`, set **before** acquisition (a throw during open is not evidence nothing was written), read together with the handle in a single critical section, and `clearLogs` after close now returns `durable: !created`. The fix surfaced and closed two adjacent races: a torn handle/flag read that produced the one impossible-and-dangerous combination, and an open/open race that could install a writer no purge could reach. The Kotlin adapter had no lock at all; it gained one and mirrors iOS method-for-method. Residual gap: the native halves are pinned by **zero tests on either platform** (finding C8).

**#2 ESLint enumeration (partial).** `logMessage` is in `LOG_METHODS`/`OPTIONS_METHODS` (`shared.js:53/:65`), `scopeMetadata` in `METADATA_OPTION_FIELDS` (`:75`), all reproduced through the real Linter. The exhaustiveness test (`__tests__/eslintPlugin.test.js:1344-1390`) enumerates both prototypes bidirectionally — the structural fix. Missed: the one dispatch site the prior finding named by line, `rules/no-derived-correlation.js:155`, was never touched (finding C9), and the test's prototype boundary is what let the constructor bypass (C2) and the config-surface holes through.

**#3 Android tests (partial).** The tautology is gone — tests now read real POSIX bits and assert exact permission sets that fail under umask 022 with a no-op `restrictToOwner`. But every new assertion exercises the test-only `PlatformIo.Jvm`; the `AndroidPlatformIo` that ships appears in zero test files (findings C3/C4).

**#4 Backup exclusion (partial).** The ownership rule is now "mkdir decided it" — securing applies only to the leaf the library's own `mkdir` created; `EEXIST` routes to a mutate-nothing `inspect()`. Class-level fix, correctly reasoned. But the un-asserted re-run took the *reporting* with it: the one call that actually secures the directory discards the `Shortfall` (finding C11).

**#5 iOS backoff (partial).** `steadyMillis()` (`DispatchTime`, `ios/LogFileWriter.swift:608-610`) now drives reopen and rotation backoff; file *age* correctly stays on `Date()` (compared against on-disk dates — matches Android's split). `writableHandle(ignoringBackoff:)` exists and is wired from `syncNow()`. Two residues: the bypass lacks the `terminated` guard every sibling reopen site has (C5), and wall-clock deadline math survives in `LogWriterRegistry.swift` while PARITY.md claims it doesn't (C12).

**#6 Android release (partial).** `dispose() → releaseHandle() → close(0.0)` is correct and arguably better reasoned than the iOS original (detach under lock, `closePending` for mid-acquire closes). But the `finalize()` backstop cannot ever run: Nitro's Kotlin `HybridObject` sits in a JNI strong-reference cycle (`CxxPart` ↔ C++ global ref) broken only by `dispose()` — so the Metro-reload leak the finding was actually about is **unchanged** (finding C13).

**#7 CI gates (closed).** Verified by execution: `turbo run build:ios --dry=json` now hashes all seven `ios/*.swift`, the podspec, `nitro.json`, all 54 `nitrogen/generated/**` and all 25 `src/**`; `build:android` hashes the Gradle/CMake/Kotlin tree. `nitrogen/` is genuinely tracked (54 files, nothing hidden behind ignore patterns), regen runs in CI, and the diff gate can now fail in all three directions.

**#9 Escaping + chunking (closed).** Escaping centralized in the single `escapeControls` chokepoint (C0, DEL, C1, U+2028/9) that every text-rendered field routes through, pinned by a property test asserting a terminal reader and a JS reader agree on line count. The Android chunker (`NativeConsoleWriter.kt:152-202`) is a line-for-line mirror of the iOS one, with a PARITY row. (But see A6/A8: the *default file formatter*, `JsonLinesFormatter`, still emits raw U+2028/9 — same asymmetry, next file over.)

## Part 2 — New findings

### Confirmed

**C1. CRITICAL — the documented ESLint setup lints zero TypeScript** *[adjudicated: refuters said high; I rate it critical for the never-log-PHI claim]*
`eslint-plugin/index.js:43-60` — `configs.recommended`/`configs.strict` are flat-config objects with no `files` key and no `languageOptions.parser`. Under ESLint 9 flat config, a config with no `files` applies only to the default set: `**/*.js`, `**/*.mjs`, `**/*.cjs`. All three shipped documents print the identical bare snippet (README.md:110, docs/PRIVACY.md:178, eslint-plugin/README.md:19). Both refuters reproduced independently against the **published 0.1.0 tarball** with ESLint 9.39.5: a project following the README verbatim flags `Log.info(`patient ${x}`)` in `b.js` and *never opens* the identical `a.tsx` — `eslint src/a.ts` prints "File ignored because no matching configuration was supplied" and exits 0. Message/correlation/subsystem have **no runtime redaction**; this lint is the only layer, and RN apps are TypeScript. The repo cannot see the problem because its own `eslint.config.mjs` inherits TS `files`/parser from `@react-native/eslint-config`.
*Fix note:* `files: ['**/*.ts','**/*.tsx']` alone is insufficient — espree then fails with parse errors, and the plugin declares no `@typescript-eslint/parser` dependency or peer. The config must compose with `typescript-eslint` and the docs must show the working setup. Add a consumer-shaped CI fixture: a scratch project with one `.ts` violation that the documented config must flag.

**C2. HIGH — `new ScopedLogger(...)` turns off all four rules** (`eslint-plugin/shared.js:1527`)
`classifyReceiver` recognizes only `.scoped()` call expressions; there is no `NewExpression` branch, so the constructor result is not a logger for any rule. `ScopedLogger` is a root export whose constructor takes correlation and subsystem — the two unredactable channels — directly. Reproduced with the real Linter: the `.scoped()` form reports `no-derived-correlation:derived` + `literal-subsystem:dynamic`; the `new` form is silent, including for `{ [patient.id]: 1 }` computed keys. The exhaustiveness test explicitly `continue`s on constructors (`eslintPlugin.test.js:1313, :1372`), and `docs/API.md:64-65`'s claim that "the ESLint rules read both" is untrue for this path.
*Fix:* add a `NewExpression` branch to `classifyReceiver`, remove the constructor exemption from the exhaustiveness test (or justify it in an explicit not-emitting list), and correct API.md.

**C3. HIGH — the published package is ESM-only; a consumer's Jest cannot import it** (`package.json:5`)
No `require` condition in `exports`, no CJS target in builder-bob; bob writes `lib/module/package.json` = `{"type":"module"}`. RN's stock Jest `transformIgnorePatterns` excludes this package from Babel. Reproduced with the real tarball extracted into a consumer's `node_modules`: `require('react-native-nitro-logger')` fails under a stock RN Jest setup. For the telehealth app about to integrate this — whose test suite will import the logger — this bites on day one.
*Fix:* add a `commonjs` bob target and a `require` export condition (or document a `moduleNameMapper`/transform recipe, but shipping CJS is the ecosystem-correct answer for RN libraries today).

**C4. HIGH — Android's shipped `restrictToOwner` is tested by nothing** (`AndroidPlatformIo.kt:78`)
Every new secure-creation test uses the default `platform = PlatformIo.Jvm` — a *different implementation* (`File.setReadable/...`) from the `Os.chmod(448/384)` that ships (`HybridFileSink.kt:158` always passes `AndroidPlatformIo`). Swap the octal constants or invert the directory/file branch and every suite on every platform stays green while shipped builds write patient-context logs world-readable.
*Fix:* hoist the mode constants where JVM tests can pin them, and add one Robolectric/instrumented case that runs `AndroidPlatformIo.restrictToOwner` for real.

**C5. HIGH — Android never verifies the mode stuck** (`AndroidPlatformIo.kt:82`)
`Os.chmod` returns success on FUSE/sdcardfs/exFAT mounts while changing nothing; `restrictToOwner` returns `true` without reading the mode back, so no `PROTECTION` degradation bit is ever set. An app pointing the sink at `getExternalFilesDir()` gets `getStatus().degraded == 0` over a world-visible log file. iOS learned exactly this lesson — `fchmod` then `fstat` then compare (`ios/LogSecureFile.swift:193-201`).
*Fix:* read the mode back (`Os.stat(path).st_mode`) and return false on mismatch, mirroring iOS; add the Android twin of `testAModeThatCouldNotBeAppliedIsReported`.

**C6. MED-HIGH — `metadataKeyCatalog` is tighten-only and neither consumer doc says so** (`docs/API.md:43`, `docs/PRIVACY.md:99-152`)
`src/Logger.ts:125-137` intersects on every later call (source comment says so; the docs don't). PRIVACY.md now shows *two* catalog calls in the same document — a reader who follows both in order silently intersects away `ERROR_METADATA_KEYS`, killing crash metadata under `'private'` with only `droppedMetadataCount` as evidence. Related trap (unverified A-list): `buildCatalog` returns an **empty set** on the first malformed entry — one typo empties the catalog with no warning.
*Fix:* document intersect semantics + the empty-on-malformed rule in both docs; make PRIVACY.md's two snippets one; consider a `__DEV__` warning when a catalog call shrinks the set to fewer keys than either operand.

**C7. MED — `syncNow()`'s bypass reopens a terminated/fenced writer and reports `durable: true`** (`ios/LogFileWriter.swift:739`) *[refuters confirmed the guard omission, rated reachability low]*
`writableHandle(ignoringBackoff: true)` calls `attemptReopen()` unconditionally — the only reopen site in the file with no `terminated` guard; `performWrite` (:494-508) and the purge (:1213) both guard first, with comments naming the exact harm (leaked descriptor for the process lifetime; an empty file where a purge just promised none). `syncNow` then sets `lastSyncSucceeded = true`, so `flush` answers `durable: true` from a writer the caller has finished with.
*Fix:* one-line guard — mirror `:1213`'s `terminated ?` check.

**C8. MED — the native half of the purge fix is pinned by no test on either platform** (`Package.swift:29`)
The compliance answer that ships on a device is produced in the two adapters; neither branch has coverage (`grep mayHaveArtifacts swift-tests/ android/src/test/` → nothing; the adapters are correctly excluded from the Nitro-free test targets). Revert `durable: !created` and all 875 tests stay green.
*Fix:* extract the handle+flag state machine into a Nitro-free type both adapters delegate to (the repo already has this pattern — `PlatformIo`, `NativeConsoleWriter`), and pin never-opened / opened-then-closed / close-during-open there.

**C9. MED — `no-derived-correlation` still hardcodes `'log'` for spread/apply** (`eslint-plugin/rules/no-derived-correlation.js:155`)
The exact line the prior review named; `git show 0e96484` touches nothing under `rules/`. Through the real Linter, `Log.log(...args)` reports `no-derived-correlation:unanalyzable`; the identical `Log.logMessage(...args)` doesn't. Same hand-maintained-surface defect, one layer down.
*Fix:* `OPTIONS_METHODS.has(call.method)` instead of the literal; export `OPTIONS_METHODS`; add the three `logMessage` spread/apply/bind fixtures.

**C10. MED — the rotation-artifact permission guard is satisfied by the sidecar** (`LogFileWriterTest.kt:695`)
`artifacts.size > 1` is meant to prove rotation happened, but `app.log.meta` is written on every open, so `{app.log, app.log.meta}` satisfies the guard with zero rotations — the same vacuous-pass defect the commit message says it caught in the PRUNE sibling.
*Fix:* guard on archive names specifically (the existing `isArchiveName`/stamp predicate).

**C11. MED — a failed backup-exclusion/protection-class application is now unreportable** (`ios/LogWriterRegistry.swift:165`)
`resolve()` wins the `mkdir` and is the only call that ever reaches `secure(isDirectory:)` — and it discards the returned `Shortfall`. The two callers that *do* consume Shortfalls structurally hit `EEXIST → inspect()`, which by design reports only permissions. Pre-fix the unconditional re-assert also re-reported; the re-assert was correctly removed, the reporting went with it.
*Fix:* return the Shortfall from `resolve()` and fold it into the writer's initial `degraded`.

**C12. MED — wall-clock deadlines survive one file over, and PARITY.md:208 now claims they don't** (`ios/LogWriterRegistry.swift:392`)
`LogFileHandle.close` budgets three waits via `Date()`-based `remaining(until:)`; `acquire`'s 5s wait uses `NSCondition.wait(until:)` (CLOCK_REALTIME); and `LogFileWriter.swift:1099` itself still does `purgeLock.lock(before: Date()...)` — contradicting the new doc comment at `:605-607` ("DispatchTime for every elapsed-time question in this file"). An NTP step during teardown turns a 200 ms close budget into up to 30 s per leg. Android's counterparts are all monotonic.
*Fix:* move the three sites to `DispatchTime` the way `LogWriter.close` (:766) already does; correct or scope the PARITY row.

**C13. MED — `finalize()` is unreachable; the Metro-reload leak is unchanged** (`android/HybridFileSink.kt:92`)
Nitro 0.36's Kotlin `HybridObject` is kept alive by a JNI strong-reference cycle that only `dispose()` breaks; neither C++ destructor calls it, so ART can never collect the object and `finalize()` never runs. The `dispose()` half of the fix is real — but the backstop half is dead code, and the dev-reload `CONFIG_CONFLICT` wedge survives wherever the JS side doesn't call `dispose()`.
*Fix:* delete the `finalize()` (it documents a guarantee that doesn't exist), state the real lifecycle contract in PARITY.md, and consider a registry-level stale-claim recovery (e.g., reclaim on `open` when the holding object is the same process + config).

## Part 3 — Quality comparison vs SwiftLogger

| Dimension | RN | Swift | Margin |
|---|---:|---:|---|
| Native file-writer robustness | **9** | 6 | decisive |
| Test rigor and honesty | **8.5** | 8 | narrow |
| Public API design & ergonomics | **8** | 7 | split (see below) |
| Data-protection / injection hardening | **9** | 5 | decisive |
| Documentation | **9** | 6 | clear |
| Architecture & concurrency | **9** | 7 | structural |

### File-writer robustness (9 vs 6)

RN wins all four stress scenarios the judges posed. **Clock step:** every elapsed-time question on RN sits on a monotonic clock; SwiftLogger has no monotonic clock anywhere — `Date().timeIntervalSince(lastReopenAttempt)` (`FileDestination.swift:496`) means a backward NTP correction wedges reopen for the duration of the step. **Force-kill mid-rotation:** RN stages gzip to `.part`, renames on success, sweeps orphans at open; Swift compresses straight to the final `.gz` name, so a kill leaves a truncated archive that permanently matches the retention regex and gets handed to anyone collecting archives. **Torn writes:** RN trims a torn tail at startup via `pread`/`ftruncate` through the same descriptor and rolls failed writes back to the fstat'd record boundary; Swift only counts the loss and leaves the torn bytes. **Out of disk:** RN bounds every wait and reports `durable`/`timedOut`/`pendingBytes`; Swift's `flush()`/`forceSave()` are unbounded `queue.sync` — reached synchronously from the uncaught-exception handler, where a wedged volume hangs the crash handler and the chained previous handler never runs. The genuine tie: both do `st_nlink == 0` deletion detection on a stride-8 cadence (the RN comment is a near-verbatim descendant of the Swift one). Swift's one real edge: it writes loss notices *into the log file*, so evidence of drops survives a force-kill; RN's loss counters die with the process.

### Test rigor (8.5 vs 8)

The closest dimension, and not decided by count. RN wins on mutation resistance exactly where Swift goes soft: exact archive counts vs `!found.isEmpty` at nine Swift sites; explicit positive controls against vacuous passes (`"nothing rotated, so this asserted nothing"`) vs four Swift rotation assertions that pass if rotation never fires; a 200-round × 5-seed fault-injected conservation property test (`batcher.test.ts:801-877`) and syscall-level injection seams Swift has no equivalent of; and the SwiftLogger-goldens fixture *generated from SwiftLogger's own formatter* rather than typed out. Swift counter-punches with world-class oracle discipline — differential ISO8601 testing over a six-century sweep plus literal pins specifically against co-drift, and the `/usr/bin/gunzip` subprocess round-trip — but carries five zero-assertion tests (three sitting beside demonstrably better versions in the same file) and no short-write coverage. The honesty ledger cuts at RN too: the Nitro adapters are excluded from both native test targets (that's findings C8 and the `Int(exactly:)` bridge guard tested 7× on Android, 0× on iOS), and 289 of the 651 Jest tests are doc-parity/lint guards, not library behavior.

### API design (8 vs 7 — a split decision)

RN wins **only because the dimension weights misuse resistance**; on coherence, discoverability, and deprecation hygiene Swift clearly wins. RN's privacy API is the difference: opaque frozen markers in module-private WeakMaps with no exported unwrap, marker types unrepresentable in what destinations see, monotonic tighten-only config, ambiguity resolving to `'private'`, destinations treated as untrusted, and a deliberately absent `reset()` with the reasoning inline. Swift's counter-case is real: a far tighter chained surface (`Log.fileLogging(true)` vs three imports and a constructor), `@autoclosure` laziness honored across every bridge, two properly-reasoned deprecations against RN's zero, and a documented formatter-reentrancy guarantee RN never has to make. RN's deductions: the catalog trap (C6) is the sharpest footgun in the API and lives only in a source comment, and README.md:98's "a dependency cannot loosen your setting" over-claims while `new Logger()` yields a public-default instance with a live console destination. Swift's deduction of note: its README teaches force-unwrapping a failable initializer that's failable precisely because disks fill.

### Privacy / injection hardening (9 vs 5 — the flagship gap)

Not a maturity artifact: a scope gap plus a strictly-dominating injection implementation. RN escapes C0, DEL, **C1**, and U+2028/9, and solved the multi-line-message forgery Swift's plan declared unsolvable — split on five line-terminator forms, indent continuations under a column no real header can occupy — so crash traces stay readable *and* unforgeable. Swift's escaper stops at `< 0x20 || == 0x7F`: U+0085 and U+2028 pass raw, making README.md:194's "cannot forge a log line" an over-claim, with two demonstrated hostile message sources (`exception.reason`, arbitrary swift-log text). On data protection Swift simply has none: 0644 world-readable log files on the macOS it supports, no protection class, no backup exclusion, no purge API, `privacy: .public` on every os_log field — and the README silent on all of it. RN's own honest weaknesses are the flip side of its design: three of four public-by-contract channels rest entirely on the (currently TypeScript-inert — C1!) lint layer, and the out-of-box default is `'public'` with no catalog — the safe configuration is opt-in, disclosed but real. Notably, RN's PARITY.md is the only place *either* repo's escaping gap is written down, including the line "matching the reference implementation is not the same as being safe."

### Documentation (9 vs 6)

Decided by enforcement and release-truth, not prose. RN's docs are executable: every ```ts fence typechecked in CI, the API reference diffed against real exports in both directions through the TypeScript parser, links resolved against the npm tarball manifest. Every quantitative claim spot-checked was exact (chunk bytes, batch tunables, purge-after-dispose semantics, test counts). Swift's README is well-organized and accurate against `main` — but it *documents an unreleased tree*: the install snippet pins `from: "2.1.0"` while the newest tag is 2.3.0 and `2.3.0..HEAD` is 32 commits, so the entire Formatters/gzip/`maxFileAge`/Buffering/Recovery/Draining/Thread-Safety story describes code no released version contains, with no marker saying so, and zero documentation jobs in CI to catch it. RN's own doc gaps: no `pod install`/Expo/toolchain setup guidance at all (the most likely first-hour failure), and `PLAN.md` ships at the root with drifted content and no "superseded" banner.

### Architecture & concurrency (9 vs 7)

RN's failure accounting is one coherent protocol — the observed/acked/confirmed cursor triple enforcing "a loss can be reported twice; it cannot be reported zero times" at exactly the four places naive implementations lose a loss — where Swift's equivalent is two integers zeroed at snapshot with no public way to ask whether anything was lost. RN bounds every wait with single-budget deadlines threaded across legs; Swift has no deadline anywhere, including the `applicationWillTerminate` path its own docs recommend. Swift's genuinely excellent piece — the retiring-collector pattern in `mutateConfig`, with flush and ARC release both deferred past the lock and pinned by `withExtendedLifetime` — is a subtle deadlock correctly found and fixed with proving tests. But the net flow of invariants has reversed: RN's `ignoringBackoff` comment says it was "ported back from SwiftLogger… the port dropped it," while the monotonic clock and `rotationBlockedUntil` now exist only on the RN side.

### Lessons worth back-porting to SwiftLogger

1. **Monotonic backoff clocks** — `Date().timeIntervalSince` at `FileDestination.swift:496/506` is the exact wedge class RN just fixed; Swift has no `DispatchTime` anywhere.
2. **Rotation backoff** — after a failed `moveItem`, Swift re-enters rotation (fsync+close+rename+open) on every flush, indefinitely, on an already-unhealthy device.
3. **Stage gzip to `.part` + rename** — a force-kill currently leaves a truncated `.gz` that permanently satisfies the retention regex.
4. **Deadline-bounded flush** — `queue.sync` from the exception handler can hang the crash path and suppress the chained previous handler.
5. **C1/U+2028-9 escaping** — closes the README over-claim; the RN escaper is a drop-in reference.
6. **Doc gates** — a `check-doc-samples` equivalent (compile every README snippet) and a release-vs-README truth check would have caught the 2.1.0-pin/unreleased-features drift.
7. **In-band loss notices** are the one Swift feature RN should port *forward*: RN's loss evidence currently dies with the process.
