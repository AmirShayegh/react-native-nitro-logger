# Appendix A triage — all 36 items adjudicated

Companion to `REVIEW-2026-07-29.md`, whose Appendix A listed 36 lower-tier
findings that were reported by finder agents, deduplicated, and then **cut from
refutation at the top-18 severity line**. They were carried unverified, which
made them the one part of that review nobody had checked and nobody had
dismissed either.

Every one of them has now been verified against the tree as it stood on
2026-07-30 — read, and where the claim was about behaviour, reproduced — and
given a disposition. Nothing here is closed on the strength of the finder's
description alone.

**Result: 34 real, 2 not defects as reported.** Of the 34: 19 had already been
closed by work shipped between the review and this triage, and 15 were fixed
here, in three reviewed batches. One of those 15 — A30 — was real only in part;
its premise was a deliberate invariant and its error string was the defect.

## Fixed in this triage — 14

### Batch (a) — native code, `3b7faff`

**A31 — the real bug of the 36.** Android's
`LogFileWriter.writableStream(ignoringBackoff = true)` had no `terminated`
guard, so `close()`'s own flush could reach `syncNow()` → `reopen()` and
**recreate the directory, log file and sidecar it was closing**; a `flush()`
landing after the close barrier reopened unconditionally. iOS had fixed exactly
this as C7 and that commit touched no Android file. Guard ported, Kotlin twin of
the iOS test added — asserting no artifacts are recreated, not merely that no
stream is returned. Mutation: remove the guard, red.

**A14 — `getLogFilePaths()` kept the conflation `clearLogs` was cured of.** It
was the only no-handle path in either adapter that ignored the lifecycle, so
opened-wrote-closed answered `[]` over files still on disk, indistinguishable
from never-opened. Fixed at both adapters against the lifecycle table, which
gained the `getLogFilePaths` row and its transition tests on both platforms.

**A28 — the logcat tag is caller-supplied and was unbounded** against ~296 bytes
of headroom, so a long category silently truncated the tail of every entry: the
exact failure the chunker exists to prevent. The stored tag is capped and the
chunk budget is computed from its real length. Test asserts no byte loss for a
long tag.

**A20 — intermediate directories got the mode and nothing else**, while the file
promised all three to any directory it creates. They now go through the same
securing path as the leaf. (Batch (c) revisits this: see A19.)

### Batch (b) — tests, gates and CI, `c6c7fc2`

**A6 — the only multi-byte chunking test passed if chunking was skipped
entirely.** Reproduced by reasoning through each assertion against a
`listOf(message)` stub, then fixed with a piece-count assertion and per-piece
fit. Mutation: stub `chunks()` to identity, red.

**A18 — the ROTATION degradation test lacked the root guard its PRUNE sibling
has** and fails red under a root JVM. Guard added, and the other
permission-dependent tests swept for the same shape.

**A15 — `MemoryFileSink.clearLogs` diverged from both real adapters twice**:
`failedPaths: [path]` where both natives report `[]`, and a hard-coded
`durable: false` where the rule is vacuous-`true` for never-opened. Dead code
today, fixed anyway — a future `FileDestination` change must not inherit a lying
double.

**A21 — the iOS monotonic waits had no test seam.** Reverting `steadyMillis()`
to `Date()` left the entire Swift suite green. `LogWriter.Steady` is now
injected beside `rawWrite`/`compressor` and forwarded through `acquire`, which
is load-bearing: writers are only ever built through the registry. Stated
non-proof in the docstring — the wall clock is not injectable, so this pins that
the backoff follows the seam rather than demonstrating a real NTP step. *First
mutation discarded*: moving only the read to `Date()` mixed clock bases and
reddened four tests including a pre-existing sibling; the faithful reversion
(read and write) reddens only the new test.

> **Closed in 0.3.0.** The wall clock is injectable now — `LogWriter.Clock`,
> the twin of Android's `clock`, forwarded through `acquire` the same way
> `Steady` is. It was added for a different reason than parity: the age tests
> measured time by sleeping, and under `swift test --parallel` a loaded machine
> could let more than the 50 ms threshold pass between creating the file and
> writing to it, so the *write* rotated and every later count was off by one.
> The suite failed a different subset on each run. Ages are now moved rather
> than waited for, and archive expiry — which is a question about file mtimes,
> not about the clock — backdates the files instead.

**A23 — the turbo hash flap was not harmless.** Both native jobs gated JDK
install, SDK licences, the Gradle cache, Xcode select and `pod install` on a
probe hash, while the build below computed its own; turbo 2.10.7 returns one of
two hashes at random for an untouched tree. Hit on the probe, miss on the build,
and gradle runs with no JDK. The probes are deleted rather than the build
re-gated: with the variable gone there is no value that can be wrong. An inert
condition naming a step id the workflow does not contain went with it.

**A3 — `build:ios` hashed `ios/*.swift` flat while the podspec compiles
`ios/**/*.{swift,m,mm}` + `cpp/**`.** Latent, and the glob was proved
load-bearing using the repo's own hash-SET method over six runs rather than a
single sample, since the documented flap makes single samples meaningless in
both directions.

### Batch (c) — lint and design, `bb9508a`

**A16 — `installErrorHandler({ subsystem: patientId })` was invisible to the
whole plugin.** Every subsystem and correlation rule starts from a receiver and
a free function has none, so the one name attached to *every* uncaught-error
entry went unlinted. New `FREE_FUNCTION_OPTION_CHANNELS` table matched by
verified import — a re-export barrel is a stated cost, unchecked until its
module joins `loggerModules`, with both a negative and a configured-positive
fixture. Exhaustiveness pinned from the TypeScript AST.

**A32 — one defect reported twice.** An unreadable options object is unreadable
for every metadata field at once, so `no-computed-metadata-key` reported
`Log.log('m', { ...opts })` twice at byte-identical ranges. Deduplicated by node
identity.

**A19 — the writer was claiming `<Library>/Logs`,** a directory the host app is
equally entitled to use, with a persistent directory-wide backup exclusion and
an inherited protection class it could not see. Now mode-only there, decided in
`LogSecureFile` by canonical identity, per directory, at creation. The first
implementation compared strings in the adapter and was wrong twice — a second
spelling of the same path claimed it *in full*, and a claim threaded from the
caller could only describe the leaf, so `<Library>/Logs/mine` claimed `Logs` on
the way past. Both are now tests.

**A29 — directory securing was path-based and the only comment on the window
denied it.** Now descriptor-based from immediately after the `mkdir`. The
comment states which window is which: a symlink at the name when it opens is
refused; a replacement after the descriptor is held is detected and reported as
a shortfall; a real directory swapped in between the `mkdir` and the `open` is
neither, and needs the same-uid attacker `PRIVACY.md` excludes.

**A30 — real in part.** Its premise, "a close during in-flight open makes the
next open fail 'already open' on a closed sink", is a deliberate, table-driven,
twice-tested invariant and not a defect: close during `opening` moves to
`closePending`, and `beginOpen` refuses until the in-flight acquisition lands.
What was real is the *error string* — `beginOpen` returned a bool, so a sink
still cancelling an earlier open said "already open", which tells a caller to
stop where the truth was "retry". It returns a `Claim` on both platforms now,
and every existing refusal assertion names which refusal.

## Not defects as reported — 2

Recorded rather than fixed, with the reason.

**A1 — "neither Android release hook is pinned by a test".** The release
*rules* have been pinned on both platforms since C8 (`FileSinkLifecycleTest`).
What is untestable is the *hooks* — `dispose()` wiring and `finalize()` — which
need a live Nitro runtime. Absorbed into the C13 harness, which is exactly that
runtime. The iOS handle-deinit backstop has no Android equivalent to test, and
that asymmetry is already a PARITY row.

**A22 — "blocking teardown on ART's finalizer thread".** Moot on the current
tree: `finalize()` is unreachable (the C13 spike proved the JNI strong-reference
cycle) and now passes deadline `0.0`, non-blocking by trace through
`clampDeadline` → `close` → `flushUntil`. One residual is recorded for the C13
design rather than fixed here: the registry lock is held across `acquire`'s real
I/O, so a finalizer racing an open could block without a deadline. Unreachable
today; the owner-token release must not inherit it.

A third — A30 — was half of each, and is written up with the fixes above rather
than here: its premise was an invariant working as designed, and its error
string was a real defect.

## What this triage does not establish

- **Ordering.** These 36 were never refuted, so a finding here was believed on
  verification done during this triage, not on the review's adversarial pass.
  Where verification meant reading rather than reproducing, the row says so.
- **That the review found everything.** 54 deduplicated candidates went into
  that funnel. This closes the 36 it set aside; it says nothing about what no
  finder looked for.
- **The native halves of A14 and A31 on a device.** Both are pinned by unit
  tests on their own platform's toolchain. The instrumented job covers the
  Android writer on an emulator; neither adapter's Nitro surface is exercised by
  a running app until the C13 harness lands.
